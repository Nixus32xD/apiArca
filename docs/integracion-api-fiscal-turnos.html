Documento de integracion con API Fiscal ARCA/AFIP

Guia para implementar la conexion desde una aplicacion externa de turnos/trabajos hacia el microservicio fiscal.

Proyecto API: apiArca
Rutas base verificadas: /api/fiscal/*
Fecha del documento: 29/06/2026

Objetivo: que la aplicacion externa pueda configurar una empresa fiscal, cargar o completar credenciales ARCA, emitir una factura cuando finaliza un turno/trabajo, guardar la respuesta fiscal y generar su propio PDF usando los datos devueltos por esta API.

1. Alcance de responsabilidades

Responsabilidad API Fiscal Aplicacion externa
Comunicacion con ARCA/AFIP Si. Maneja WSAA, WSFEv1, CAE, CAEA, token, sign y numeracion. No debe llamar directamente a ARCA.
Credenciales fiscales Guarda certificado, clave privada y tickets cifrados. Debe ofrecer pantallas para generar CSR o enviar certificado a esta API.
Emision de factura Autoriza comprobante y devuelve CAE/numero/estado. Debe llamar al endpoint al finalizar el turno/trabajo.
PDF de comprobante No genera el PDF comercial. Debe armar el PDF con datos propios + datos fiscales devueltos por la API.
Idempotencia Evita duplicados por business_id + idempotency_key. Debe generar una clave estable por turno, por ejemplo turno-123-factura.

2. Configuracion base de conexion

La aplicacion externa debe guardar esta configuracion en backend, no en el frontend publico.

Campo Ejemplo Uso
FISCAL_API_URL https://tu-dominio.com/api/fiscal URL base de esta API.
FISCAL_API_TOKEN token-secreto-largo Token interno configurado en FISCAL_API_TOKENS de la API.
FISCAL_BUSINESS_ID empresa-amigo-1 Identificador estable de la empresa fiscal en la API.

Headers obligatorios

Authorization: Bearer token-secreto-largo
Content-Type: application/json
X-Trace-Id: turno-123

X-Trace-Id es opcional, pero recomendado. Permite rastrear en logs una operacion concreta de la aplicacion externa.

3. Vistas que debe crear la aplicacion externa

3.1 Vista: Conexion con API Fiscal

Objetivo: guardar la URL, token y empresa fiscal que usara la aplicacion externa.

Campos sugeridos:

  • URL base de API fiscal.
  • Token interno.
  • business_id / empresa fiscal activa.
  • Boton "Probar conexion".

Prueba recomendada: si la empresa ya existe, llamar a:

GET /api/fiscal/companies/{business_id}/status

3.2 Vista: Empresa fiscal

Objetivo: registrar o actualizar la empresa que va a facturar.

Endpoint:

POST /api/fiscal/companies

Campos de pantalla:

Campo UI Campo API Validacion
Identificador empresaexternal_business_idTexto estable, max. 120 caracteres.
CUITcuit11 digitos, sin guiones.
Razon sociallegal_nameTexto requerido.
Condicion fiscalfiscal_conditionmonotributo, responsable_inscripto o exento.
Ambienteenvironmenttesting o production.
Punto de ventadefault_point_of_saleNumero habilitado en ARCA.
Tipo comprobante defaultdefault_voucher_typeOpcional si se usa invoice_mode=auto.
HabilitadaenabledBooleano.

Request ejemplo:

{
  "external_business_id": "empresa-amigo-1",
  "cuit": "20123456789",
  "legal_name": "Empresa Demo",
  "fiscal_condition": "monotributo",
  "environment": "testing",
  "default_point_of_sale": 1,
  "default_voucher_type": 11,
  "enabled": true,
  "onboarding_metadata": {
    "source": "app-amigo"
  }
}

3.3 Vista: Credenciales ARCA - flujo recomendado con CSR

Objetivo: que la API genere la clave privada y el CSR. La aplicacion externa solo muestra el CSR y luego sube el certificado emitido por ARCA.

Recomendado: no guardar clave privada en la aplicacion externa. La API ya la guarda cifrada. La aplicacion externa debe actuar como pantalla/proxy administrativo.

Paso A - Generar CSR:

POST /api/fiscal/companies/{business_id}/credentials/csr
{
  "key_name": "empresa-amigo-prod.key",
  "common_name": "empresa-amigo-prod",
  "organization_name": "Empresa Demo",
  "country_name": "AR"
}

La pantalla debe mostrar:

  • credential.id: se usara luego para subir el certificado.
  • credential.status: inicialmente pending_certificate.
  • csr: texto que se carga en ARCA/AFIP para emitir el certificado.

Paso B - Subir certificado emitido por ARCA:

PUT /api/fiscal/companies/{business_id}/credentials/{credential_id}/certificate
{
  "certificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
  "active": true
}

La API valida que el certificado corresponda a la clave privada generada. Si no coincide, devuelve 409 certificate_private_key_mismatch.

Paso C - Probar credenciales:

POST /api/fiscal/companies/{business_id}/credentials/test

Si responde correctamente, la empresa ya puede facturar.

3.4 Vista alternativa: carga directa de certificado y clave privada

Usar solo si el cliente ya tiene certificado y clave privada. Es menos recomendable porque la aplicacion externa manipula datos sensibles.

PUT /api/fiscal/companies/{business_id}/credentials
{
  "certificate": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
  "private_key": "-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----",
  "passphrase": null,
  "certificate_expires_at": "2027-04-28",
  "active": true
}

3.5 Vista: Estado fiscal

Objetivo: mostrar si la empresa esta lista para facturar.

GET /api/fiscal/companies/{business_id}/status

Campos importantes de respuesta:

{
  "data": {
    "business_id": "empresa-amigo-1",
    "environment": "testing",
    "enabled": true,
    "ready": true,
    "status_label": "Listo",
    "message": "Empresa fiscal operativa.",
    "defaults": {
      "point_of_sale": 1,
      "cbte_type": 11
    }
  }
}

Si ready=false, la aplicacion externa no deberia permitir emitir facturas.

3.6 Vista: Diagnostico fiscal

Objetivo: dar soporte cuando algo falla en certificados, token o conexion con ARCA.

GET /api/fiscal/companies/{business_id}/diagnostics

Usar esta vista para operadores internos. No es necesaria para el cliente final.

3.7 Vista: Catalogos fiscales

Objetivo: consultar puntos de venta y actividades habilitadas en ARCA.

GET /api/fiscal/companies/{business_id}/points-of-sale
GET /api/fiscal/companies/{business_id}/activities

La aplicacion externa puede usar estas respuestas para cargar combos de seleccion o validar configuracion.

3.10 Vista: Reconciliacion y reintentos

Objetivo: resolver estados inciertos sin duplicar comprobantes.

Estado API Accion de la app externa
authorizedGuardar datos fiscales y generar PDF.
rejectedNo generar PDF fiscal. Mostrar error y corregir datos.
errorMostrar error. Puede reintentar solo si el flujo operativo lo permite.
uncertainNo emitir de nuevo. Primero reconciliar contra ARCA.
 
POST /api/fiscal/documents/{document_id}/reconcile
POST /api/fiscal/documents/{document_id}/retry

Regla clave: si la API devuelve uncertain, la aplicacion externa no debe hacer otro POST /documents con otra clave. Debe usar la misma respuesta/documento y llamar a reconcile o retry.

5. PDF/comprobante que debe generar la aplicacion externa

La API fiscal devuelve datos autorizados, pero el PDF debe ser generado por la aplicacion externa porque ahi estan los datos comerciales del turno/trabajo.

5.1 Datos comerciales desde la aplicacion externa

  • Nombre, CUIT, condicion fiscal y domicilio del emisor.
  • Cliente: nombre/razon social, documento, domicilio y condicion fiscal cuando aplique.
  • Fecha del turno/trabajo.
  • Detalle de servicio o trabajo realizado.
  • Items, cantidades, precios unitarios, descuentos si aplica.
  • Subtotal, IVA, tributos, exentos/no gravados y total.
  • Forma de pago, si la aplicacion externa la necesita mostrar.

5.2 Datos fiscales devueltos por la API

  • Tipo de comprobante: document_type y cbte_type.
  • Punto de venta: point_of_sale.
  • Numero: number.
  • CAE/CAEA: authorization_code o cae.
  • Vencimiento CAE: cae_expires_at.
  • Estado fiscal: fiscal_status.
  • Empresa fiscal: company.cuit, company.legal_name, company.fiscal_condition.

5.3 QR fiscal

El PDF deberia incluir QR fiscal cuando corresponda segun normativa vigente. La aplicacion externa puede construirlo con los datos de la factura y la respuesta de la API.

URL base usada habitualmente por ARCA/AFIP:

https://www.afip.gob.ar/fe/qr/?p={base64-json}

JSON base para el QR:

{
  "ver": 1,
  "fecha": "2026-06-29",
  "cuit": 20123456789,
  "ptoVta": 1,
  "tipoCmp": 11,
  "nroCmp": 11,
  "importe": 12100.00,
  "moneda": "PES",
  "ctz": 1,
  "tipoDocRec": 96,
  "nroDocRec": 30123456,
  "tipoCodAut": "E",
  "codAut": 12345678901234
}

Mapeo: tipoCmp = cbte_type, nroCmp = number, codAut = authorization_code. Para CAE usar tipoCodAut="E"; para CAEA validar el codigo requerido en la implementacion fiscal vigente. Referencia oficial: https://www.afip.gob.ar/fe/qr/

7. Manejo de errores

Los errores controlados devuelven JSON con esta forma:

{
  "message": "Fiscal company was not found.",
  "error_code": "company_not_found",
  "context": {
    "identifier": "empresa-amigo-1"
  }
}
HTTP Causa comun Accion recomendada
401Falta token.Revisar header Authorization.
403Token invalido.Revisar FISCAL_API_TOKENS.
404Empresa/documento no encontrado.Verificar business_id o ID fiscal.
409Falta credencial, certificado vencido, empresa deshabilitada o retry bloqueado.Mostrar mensaje y usar status/diagnostics.
422Payload invalido o reglas fiscales incumplidas.Corregir campos del formulario.
500Error inesperado.Guardar respuesta, trace id y revisar logs.

8. Ejemplo C# / .NET con HttpClient

using System.Net.Http.Headers;
using System.Text;
using System.Text.Json;

var client = new HttpClient();
client.BaseAddress = new Uri("https://tu-dominio.com/api/fiscal/");
client.DefaultRequestHeaders.Authorization =
    new AuthenticationHeaderValue("Bearer", "token-secreto-largo");
client.DefaultRequestHeaders.Add("X-Trace-Id", "turno-123");

var payload = new
{
    business_id = "empresa-amigo-1",
    origin = new { type = "sale", id = "turno-123" },
    invoice_mode = "auto",
    concept = 2,
    point_of_sale = 1,
    customer = new
    {
        name = "Juan Perez",
        document_type = "DNI",
        document_number = "30123456",
        iva_condition = "consumidor_final"
    },
    amounts = new
    {
        imp_total = 12100,
        imp_neto = 10000,
        imp_iva = 2100,
        imp_trib = 0,
        imp_op_ex = 0,
        imp_tot_conc = 0
    },
    currency = "PES",
    currency_rate = 1,
    idempotency_key = "turno-123-factura"
};

var json = JsonSerializer.Serialize(payload);
var content = new StringContent(json, Encoding.UTF8, "application/json");
var response = await client.PostAsync("documents", content);
var body = await response.Content.ReadAsStringAsync();

if (!response.IsSuccessStatusCode)
{
    throw new Exception(body);
}

// Guardar body.data en la factura/turno y generar PDF si status == authorized.

9. Checklist final para el desarrollador externo

  1. Crear pantalla de configuracion de API fiscal: URL, token y business_id.
  2. Crear pantalla de empresa fiscal y consumir POST /companies.
  3. Crear pantalla de credenciales con flujo CSR: generar CSR, mostrarlo, subir certificado y probar credenciales.
  4. Crear pantalla de estado/diagnostico fiscal para saber si la empresa esta lista.
  5. Al cerrar un turno, construir payload y llamar a POST /documents.
  6. Usar siempre idempotency_key estable por turno para evitar duplicados.
  7. Guardar respuesta fiscal completa asociada al turno.
  8. Generar PDF solo si status o fiscal_status es authorized.
  9. Si el estado es uncertain, llamar a reconcile antes de cualquier reintento.
  10. Agregar consulta por origen para recuperar comprobantes usando origin_type=sale y origin_id={turno_id}.
Conclusion: la aplicacion externa no necesita implementar logica ARCA/AFIP. Solo debe crear las vistas administrativas, enviar los payloads correctos a esta API, guardar la respuesta fiscal y generar el PDF final con sus datos comerciales mas CAE/numero devueltos por la API.
